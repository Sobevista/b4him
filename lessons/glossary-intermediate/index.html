The n8n Track · Glossary II

Twenty Words for a Workflow That Has to Hold.

What you'll be able to do: say any of these twenty words four ways — the precise definition, the one a non-technical colleague would understand, the everyday thing it's like, and the mistake it causes — and look at a workflow that runs and say which of them it is missing.

The Invariant

A word you cannot say four ways — technical, plain, analogy, and the mistake it causes — is a word you have not learned. You have only heard it.

Why it matters: it's the same invariant as Glossary I, on purpose — one method, carried forward. It bites harder here, because almost every word on this page names a failure you cannot see: a record written twice, a record written half, a check that skipped itself, a default that turned a missing number into a believable zero. Nothing errors. The four rows are how you find out whether you knew the word or only the sound of it, before the data finds out for you. This page is a tool glossary. The invariant under it isn't.

Why This Page Exists

Glossary I is the vocabulary for getting a workflow to run. This one is the vocabulary for getting it to hold — to survive the retry, the blank input, the crash halfway through, the night nobody is watching. Glossary I pointed here more than once without saying so: Append's mistake row names a fix it never defines, and three of its rows turn on the word silently.

The source glossary only carried two words past beginner. So I went back through the rest of what we have — the intermediate curriculum itself, and the notes written as things broke — and took the words that kept showing up. Every word here, and what it means, was already in our own material. The four rows for eighteen of them were written out for this page, in the same shape as the first two. Where the curriculum already had an analogy, it's the one you'll read.

The fourth row is still the one I'd skip if I were you, so it still has its own shading. Read it before you think you need it.

Choose Your Door

  • Builder — read the PLAIN rows, then take something you've already built and break it on purpose: send it twice, send it blank, kill it halfway.
  • Architect — read TECHNICAL only; six of these words are one rulebook, and the rest are its failure modes.
  • Translator — the ANALOGY rows are yours. Most of them come straight from the curriculum, which was written with you in mind.

Where the Analogies End

Every analogy below is a ladder, and a ladder is for climbing off.

Where the analogy ends: look at who is in these pictures — a receptionist, a foreman, a site inspector, a clerk. Every one of them is a person, and a person notices things nobody told them to notice: the visitor they've seen before, the delivery that looks a bit off. A workflow notices nothing you didn't build it to notice. It can't guess that a request is a retry, can't sense that a record is half-saved, can't tell that a zero was supposed to be a number. Every analogy here quietly hands you that judgment for free. In software, the judgment is the part you have to build.

Agent

Intermediate
Technical
An LLM-powered node that can reason, make decisions, and call external tools or APIs to complete a defined objective, then return a structured result.
Plain
An AI that does more than answer — it acts. It reads a task, works out what it needs, calls the tools to get it, and hands back a result.
Analogy
A new hire with a phone and a company card. Give them a clear job and they come back with an answer. Give them a vague one and they still come back with an answer.
Common mistake
Treating an agent’s output as finished data. An agent returns whatever it generates — a polite explanation, markdown, half a JSON object — with no idea it just broke the next node. Every agent output goes through Structured Output and a Validation Block before anything downstream touches it.

Blast Wall

Intermediate
Technical
A node-level configuration that isolates a non-critical branch so its failure does not propagate to the primary execution path. In n8n: Continue on Fail on the node, usually with retries. Partial results are merged so the core transaction still completes.
Plain
A firebreak. If an optional step fails — say, an extra lookup times out — the rest of the workflow keeps going with what it has.
Analogy
Subcontractors on a building site, each walled into their own lane. The heating crew running late doesn’t send the electricians home.
Common mistake
Walling a node off and never reading what comes through the wall. Continue on Fail swallows the error and passes an item downstream that carries an error field instead of the data you wanted; every node shows green and the record is missing data. A blast wall has to mark what failed — a flag or an explicit null that the next node checks — or it isn’t a firebreak, it’s a rug.

Error Trigger

Intermediate
Technical
A separate workflow that starts with an Error Trigger node and fires when a workflow that names it throws an unhandled fatal error. In n8n you attach it per workflow — each workflow’s Settings → Error workflow — so one error workflow can watch many, but only the ones you point at it. It packages the run ID, workflow name, failed node, error message and timestamp, and sends a human-readable alert. The source calls it the Dead-Man’s Switch.
Plain
A workflow whose only job is to shout when another workflow crashes.
Analogy
The foreman’s standing order: if anything goes wrong on site and nobody reports it, his phone rings anyway.
Common mistake
An alert that arrives and says only “an error occurred.” It fails the source’s own gate: the alert has to say where the system broke — which run, which node, what error, when. The quietest version: building the handler and never attaching it. The error workflow exists, looks right, and is pointed at by nothing — so the crash it was built for rings no phone. Another is never asking what happens when the error handler itself crashes. That question has a name in Glossary III, which isn’t published yet.

Exponential Backoff

Intermediate
Technical
A retry strategy for transient failures — timeouts, rate limits, brief outages — where the wait between attempts doubles (1, 2, 4, 8 seconds) up to a maximum retry count, after which the workflow raises a final error.
Plain
If a call fails, wait and try again — and wait longer each time, so you’re not hammering a service that’s already struggling.
Analogy
Calling a busy shop. You don’t redial every second. You try again in a minute, then five, then twenty.
Common mistake
Every copy of the workflow backing off on exactly the same schedule. When many runs fail together they retry together — all at once, then all at once again. Add jitter: a random wait between 2n and 2n+1 seconds. And don’t retry what isn’t transient: a wrong key fails four times, just slower.

Fail-Open

Intermediate
Technical
A guard whose default, when its trigger doesn’t fire, is passage: no verdict, so proceed. Nobody chooses it. It is the free consequence of writing “if the check matches, act” and never writing the else-branch.
Plain
A check where “the check didn’t happen” looks exactly like “the check passed.”
Analogy
A homework tray labelled “Period 3.” One essay lands in a tray labelled “Period 3 ” — trailing space, different tray. The grading routine finds nothing wrong, and the missing essay reads as no news is good news.
Common mistake
Branching on a count. count == 0 is the honest report of both “nothing was wrong” and “I could not look” — so if the step that produced the count crashed, the empty result takes the healthy branch. Make every check say its verdict out loud — PASSED, SKIPPED, REFUSED — so “I didn’t run” can never wear the costume of “all clear.”

Half-Written State

Intermediate
Technical
A data store left partially updated because a workflow wrote mid-execution and then failed before its later writes: some fields new, others stale, the record internally inconsistent.
Plain
The workflow saved half its work and then crashed. The record looks complete. It isn’t.
Analogy
Updating a customer’s file during a phone call — note, note, note — and the call drops. The file now holds a partial, contradictory record that looks finished.
Common mistake
Treating it as no worse than a failed run. A failed run is obviously broken; a half-written record is quietly wrong, and quietly wrong outlives you. The fix isn’t better error handling at the crash point. It’s not writing until the end — Pull at Genesis, Commit at Revelation.

Hallucination

Intermediate
Technical
An LLM generating plausible but incorrect or structurally invalid output. In a data pipeline the dangerous form is structural: markdown fences around the JSON, missing keys, or a sentence where an object was expected.
Plain
The AI making something up because it had nothing real to say — or answering in the wrong shape.
Analogy
Asking for a filled-in form and getting back a friendly letter about the form.
Common mistake
Thinking it only means invented facts. In a pipeline, the common version is a blank input getting a polite “I don’t have enough information to answer that” — a sentence where your next node expected an object. That sentence crashes the write. Or worse, it gets written.

Idempotency

Intermediate
Technical
The property of an operation that produces the same result regardless of how many times it is executed with the same input. An idempotent workflow run twice with the same data produces one record, not two.
Plain
If you do the same thing twice, the result is the same as doing it once. No duplicates.
Analogy
An elevator call button. Press it once or press it ten times — one elevator comes. (A light toggle is the opposite: press it twice and you are back where you started. That is the kind of operation idempotency protects you from.)
Common mistake
Using Append without a deduplication check. If the same event fires twice (a webhook retry, a double form submission), you get two identical records. Fix: assign a unique Run_ID and check for it before writing.

Ingress Layer

Intermediate
Technical
A dedicated first stage — in n8n, typically an Edit Fields (Set) node straight after the trigger — whose only job is to ingest, normalize, label and route the incoming payload, so no raw, unvalidated external data reaches a processing node. It is the working form of Separation of Concerns.
Plain
The front desk. Everything that arrives is checked, tidied and labelled before it goes anywhere inside.
Analogy
A receptionist who takes the visitor’s card, writes it out in the building’s own format, and stamps a visit number on it before anyone goes upstairs.
Common mistake
Mapping fields straight out of the incoming payload in five different nodes. Now every node has its own idea of what the data looks like, and one renamed field upstream breaks five places instead of one. One door in; everything downstream reads the cleaned version.

Near-Miss

Intermediate
Technical
Input one notch off from valid — an old template, a consistent typo, a plural where a singular was expected — that slips past exact-match checks without triggering them.
Plain
Data that’s almost right. Close enough to look normal; wrong enough to skip your check.
Analogy
A key cut one notch off. It slides into the lock perfectly. It just doesn’t turn — and nothing tells you why the door is still shut.
Common mistake
Guarding against garbage and calling it done. Garbage looks like garbage and usually errors on its own; the near-miss is the one that sails through. We had a check that only recognised its marker word for word. One word off, and it didn’t fail — it skipped itself, and unchecked work went straight past it. The rule we took from that: near-misses refuse.

Pagination

Intermediate
Technical
An API returning a large result set in pages — by page number, offset or cursor — with a field that says whether more remain (has_next_page, next_cursor). Getting the full set means looping until that field says stop.
Plain
The API hands you the first hundred results and a note saying “there’s more.” You have to keep asking.
Analogy
Search results. Page one isn’t the whole internet.
Common mistake
Reading page one and believing it’s everything. Nothing errors — you just have the first 100 of 4,000 records. After the loop, compare your item count to the total the API reports. And give the loop a ceiling (the source uses 50 pages, then stop and log): an unbounded loop in production is its own outage.

Pull at Genesis, Commit at Revelation

Intermediate
Technical
The deterministic memory lifecycle: every read from the data store happens at the start of the workflow, all processing happens in memory, and every write happens in one operation at the end. If that one write is atomic, the store is either fully updated or untouched — never half-written. (If the final write is itself several calls, it can still fail between them; the lifecycle shrinks the danger to one moment, it doesn’t abolish it.)
Plain
Read everything first. Do the work. Save once, at the end.
Analogy
Pull the whole account history before the sales call; update the customer file once, after the call — never note by note during it.
Common mistake
Adding “just one quick save” in the middle because a later step needs the value. That one mid-flight write is the whole failure. Carry the value forward in memory and write it with everything else. Glossary I’s Workflow is the blueprint; this is the rule for when the blueprint is allowed to touch the database.

Run_ID

Intermediate
Technical
A deterministic, unique identifier assigned to each workflow execution based on event data (for example, a hash of the event source + the event’s own timestamp + key fields). Used to enforce idempotency by detecting duplicate events. The timestamp must be the one the event carries, not the time you received it — a retried webhook arrives later, and a received-at time would give the duplicate a fresh ID.
Plain
A unique tracking number generated from the event itself, used to detect and reject duplicate runs.
Analogy
A purchase order number. Derived from the vendor, date, and items ordered — so the same order always gets the same number. If the accounts-payable clerk sees a PO number they have already processed, they know it is a duplicate and reject it.
Common mistake
Using a database auto-increment ID as a Run_ID. Auto-increment IDs are assigned at write time — they cannot detect duplicates before writing. A Run_ID must be derived from the event data itself, before any write occurs.

Safe Default

Intermediate
Technical
A fallback value applied in an expression when a field is missing or null — in n8n, usually the nullish operator: {{ $json.points ?? 0 }} — so downstream nodes never receive undefined.
Plain
“If this field is missing, use this instead.”
Analogy
Writing “N/A” in a form box so the clerk doesn’t reject the whole form for one blank.
Common mistake
Defaulting a field that was required. ?? 0 on an optional bonus is a safe default. ?? 0 on an order total is a lie: the missing total becomes a real-looking zero, the log stays green, and nothing ever tells you. Defaults are for optional fields. A missing required field should stop the run.

Schema Rigidity

Intermediate
Technical
The invariant that downstream systems never receive undefined keys or raw model text: required fields and types are enforced at every boundary — a JSON Schema on model output, explicit checks and safe defaults in expressions — and missing keys are intercepted before any database or code node. The source calls it the Data Airbag.
Plain
Glossary I’s Schema says what your data should look like. Schema rigidity is actually refusing data that doesn’t.
Analogy
An airbag. You never notice it on a normal day. It exists for the one day the input hits your workflow at speed.
Common mistake
Writing the schema down and never enforcing it. A schema in a document is a hope — Glossary I already warns that the tool won’t enforce it for you. Rigidity is the check that runs on every execution, and you prove it by sending a payload with a required field removed and watching the run stop: explicitly, not silently.

Status Code

Intermediate
Technical
The three-digit number an HTTP response opens with. 2xx: success. 4xx: a problem with the request — 401 not authenticated, 403 forbidden, 404 not found, 429 too many requests. 5xx: a problem on the server — 503 unavailable.
Plain
The one-number answer that comes back before the data: it worked, it’s your end, or it’s theirs.
Analogy
The stamp on a returned letter: delivered, wrong address, refused, try again later.
Common mistake
Two of them. First, letting a 429 or a 503 flow downstream as an empty body — wire the HTTP node’s error output, or a rate limit becomes undefined in your data. Second, trusting 404 to mean “doesn’t exist.” Some services answer 404 to a request that lacks permission, so outsiders can’t even confirm the thing is there. “Fixing” the URL is the wrong fix; check the credential.

Structured Output

Intermediate
Technical
Enforcing a JSON Schema on an LLM node’s output (the node’s Output Schema / Structured Output option), declaring the required keys and their types so the response is constrained to machine-readable data.
Plain
Instead of asking the AI nicely for JSON, you hand it a form it has to fill in.
Analogy
A written scope of work for a contractor: exactly these five items, in these sizes, or the delivery is refused at the gate.
Common mistake
Believing it’s the only wall. Structured output constrains the shape; it doesn’t stop a required field coming back null, or a true arriving as the string "true". That is the Validation Block’s job. The source’s own gate asks what each one catches that the other can’t. You need both.

System Prompt

Intermediate
Technical
Instructions given to an LLM at the start of a call that define its role, behaviour, constraints and output format.
Plain
The job description you give the AI before it starts work.
Analogy
The briefing a temp gets on their first morning. A precise briefing gets the same work out of any temp. A vague one gets whatever that temp thought you meant.
Common mistake
Writing “return JSON” in the prompt and calling it enforcement. A prompt is a request, and the model will occasionally decline it; enforcement is Structured Output plus a Validation Block. And say who the model is: in our own builds a small model refused a bare instruction, then did the identical task the moment the prompt opened with a role.

Upsert

Intermediate
Technical
A write operation that updates the existing record if one with the same unique key exists, and inserts a new one if not. One operation, two outcomes, zero duplicates.
Plain
Find it by its ID. If it’s there, update it. If it isn’t, add it.
Analogy
The hotel clerk from Glossary I’s Append — finally checking the guest list before handing out a room.
Common mistake
Upserting on a key that isn’t unique — a name, an email two people share, a value that changes over time. The upsert dutifully overwrites the wrong record. The key has to exist, and be unique, before the write — which is why Upsert travels with Run_ID.

Validation Block

Intermediate
Technical
A code step placed directly after an LLM node that re-checks every key, applies safe defaults or rejects, coerces types (the string "true" to a boolean), and returns one clean, flat object — the second wall after Structured Output.
Plain
A small piece of code that checks the AI’s answer before anything else is allowed to use it.
Analogy
A site inspector who checks the delivery against the order, even after the supplier swore it was right.
Common mistake
Writing a validation block that can’t fail. If every field gets a ?? default, the block turns a broken model response into a tidy record of zeros and “Unknown” — and the source’s own review prompt asks exactly where ?? still lets bad data through. Decide which fields may default. For the rest, the block should throw.

What Isn't Here

The words for systems — workflows that call other workflows, monitors that watch them, agents that check each other, and the failures that only happen in the gaps between — are held for Glossary III, which isn’t published yet. Several mistake rows above already point there. That's the order these words were learned in: one workflow that holds, then several that have to hold together.

And one more honest note. Six of these words — Ingress Layer, Idempotency, Schema Rigidity, Blast Wall, Pull at Genesis, and the Error Trigger — are the curriculum's six rules, and each of them is taught there by breaking it first. A glossary can give you the word. Only the breaking gives you the fourth row.

Validator Gates

  1. Gate 1: Without looking, say the difference between a failed execution and a half-written state. Which one is more dangerous, and which word on this page prevents it?
  2. Gate 2: Structured Output and the Validation Block are both walls around a model's answer. Name one failure each catches that the other cannot.
  3. Gate 3: Safe Default's mistake row and Fail-Open's mistake row describe the same disease in two different places. Say what it is in one sentence.
  4. Gate 4 (own words): Pick a check you rely on — an email filter, a spreadsheet lookup, a form that validates. Feed it a near-miss on purpose: one letter off, a trailing space. Write your prediction first — flag, or silence? If it was silence, you have found a fourth row of your own.

Glossary complete — the second of three. If the four-row habit is the only thing you take from it, you got the invariant and can drop the tool. And if you take one more thing: a workflow that runs is not a workflow that holds, and the difference is almost never visible from the green tick.
